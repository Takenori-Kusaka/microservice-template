# Workload Profile（1枚のワークロード定義）

指針書 [Phase 0](../microservice-guidelines.md#phase-0意思決定) で要求する「想定RPS、tenant数、burst、payload、SLO、データ分類を1枚に記録する」ための記入テンプレート。サービスごとに1枚作成し、`apps/<serviceId>/docs/workload-profile.md` に置く。PaaS全体の合算版は本ファイルを更新する。

記入値は、指針書の以下の判断に直接使われる。

| 項目                     | 使われる判断                                                                 |
| ------------------------ | ---------------------------------------------------------------------------- |
| RPS、burst、duration     | 同時実行予算（10, 11章）、throttle値、reserved concurrency                   |
| tenant数、tier分布、skew | 分離モデル（5章）、tier別queue、cell分割時期                                 |
| payload                  | イベント包絡（claim-check要否）、DynamoDB item size、API Gateway payload制限 |
| SLO                      | Application Signals SLO、burn rate alarm、性能予算配賦                       |
| データ分類               | KMS粒度、audit log、Step Functions実行履歴の制限                             |
| 成長予測                 | quota増枠申請（11章）、cost model（15章）                                    |

記入規則：

- 数値は根拠（実測 / 契約 / 推定）を付ける。推定は幅で書く。
- 四半期ごとに見直し、変更履歴に残す。
- 「不明」のままにしない。不明なら推定値と、確定させる方法・期日を書く。
- 記入例の数値はすべて本テンプレートの例示値であり、外部出典に基づかない。容量算出式のみ出典を持つ（下記「出典」）。

## 記入例：中規模B2B PaaS（PaaS全体、Phase 1）

以下は、本テンプレートの初期想定規模に対する記入例である。実際の値は各組織で置き換えること。

### 0. 基本情報

| 項目               | 値                                           |
| ------------------ | -------------------------------------------- |
| 対象               | PaaS全体（order / worker / workflow の合算） |
| 作成日             | 2026-10-17                                   |
| 作成者 / ownerTeam | platform-team                                |
| 次回見直し日       | 2027-01-17                                   |
| 関連ADR            | ADR-0004、ADR-0016、ADR-0017                 |

### 1. テナント

| 項目                         | 値                                        | 根拠                         |
| ---------------------------- | ----------------------------------------- | ---------------------------- |
| 現在のテナント数             | 120                                       | 契約台帳                     |
| 12ヶ月後のテナント数（予測） | 300〜400                                  | 営業計画                     |
| tier分布                     | standard 100（83%）/ premium 20（17%）    | 契約台帳                     |
| 最大テナントの負荷シェア     | 18%                                       | 現行システムのaccess log集計 |
| 上位10テナントの負荷シェア   | 55%                                       | 同上                         |
| silo候補テナント数           | 2（金融系、専用鍵と監査分離を契約で要求） | 契約                         |
| 規制・契約上の分離要件       | 上記2テナント                             | 契約                         |

含意：上位10テナントで過半を占めるskewがあるため、tier別queueとtenant skew負荷試験が必須。最大テナントが18%であり20%未満のためPhase 1ではpool + bridge（tier別queue）で開始し、Phase 2でcell分割を評価する。silo 2テナントはPhase 3。

### 2. 同期API

| operation           | 平均RPS | ピークRPS | burst倍率 | p50 / p95 / p99（目標、ms） | request payload | response payload          | 読み書き比 |
| ------------------- | ------- | --------- | --------- | --------------------------- | --------------- | ------------------------- | ---------- |
| `createOrder`       | 15      | 50        | 3x        | 80 / 300 / 800              | 2KB / 32KB      | 1KB / 4KB                 | 書き       |
| `getOrder`          | 40      | 150       | 3x        | 30 / 120 / 300              | —               | 1KB / 8KB                 | 読み       |
| `listOrders`        | 10      | 40        | 2x        | 60 / 200 / 500              | —               | 20KB / 100KB（limit 100） | 読み       |
| `updateOrderStatus` | 5       | 20        | 3x        | 80 / 300 / 800              | 1KB / 4KB       | 1KB / 4KB                 | 書き       |
| 合計                | 70      | 260       | —         | —                           | —               | —                         | 読み 71%   |

| 項目                                 | 値                                                                 | 根拠           |
| ------------------------------------ | ------------------------------------------------------------------ | -------------- |
| 時間帯パターン                       | 営業時間（9〜18時 JST）に80%集中。夜間はbatch的な server-to-server | 現行access log |
| 曜日・月末・季節性                   | 月末最終3営業日はピーク1.5倍。年度末2倍                            | 同上           |
| クライアント種別                     | SPA 60% / server-to-server 35% / batch 5%                          | 同上           |
| 1テナントあたりの最大RPS（契約上限） | standard 50 / premium 200                                          | tier定義       |

### 3. 非同期 / イベント

| イベント型                         | 平均件数/秒       | ピーク件数/秒 | payload    | consumer数               | 処理時間 p95（ms） | 処理開始遅延の許容          |
| ---------------------------------- | ----------------- | ------------- | ---------- | ------------------------ | ------------------ | --------------------------- |
| `order.created.v1`                 | 20                | 70            | 2KB / 8KB  | 1（worker）              | 400                | premium 60s / standard 300s |
| `order.fulfilled.v1`               | 19                | 65            | 1KB / 4KB  | 0（将来：通知service）   | —                  | —                           |
| `fulfillment.failed.v1`            | 0.2               | 5             | 2KB / 8KB  | 0（将来：alert service） | —                  | —                           |
| `tenant.provisioning.requested.v1` | 0.001（約100/日） | 0.05          | 4KB / 16KB | 1（workflow）            | —                  | 5分                         |

| 項目                     | 値                                                 | 根拠        |
| ------------------------ | -------------------------------------------------- | ----------- |
| 下流容量制限             | 外部履行API：tenant単位 10 req/s、全体 100 req/s   | 外部API契約 |
| 順序保証が必要なイベント | なし（注文単位の状態遷移は条件付き書き込みで保護） | 設計        |
| 64KB超のpayload          | なし                                               | 設計        |

含意：worker の `maxConcurrency` 合計は外部API全体上限（100 req/s）と処理時間（0.4秒）から最大40。premium 25 / standard 15 で初期設定し、負荷試験で調整。

### 4. ワークフロー

| workflow            | 実行数/日 | ピーク同時実行数 | 所要時間（典型 / 最大） | step数      | 補償を要するstep        | Standard / Express             |
| ------------------- | --------- | ---------------- | ----------------------- | ----------- | ----------------------- | ------------------------------ |
| tenant provisioning | 100       | 10               | 2分 / 15分              | 4（+補償2） | reserve slot、provision | Standard（監査、exactly-once） |

### 5. データ

| 項目                           | 値                                                                           | 根拠           |
| ------------------------------ | ---------------------------------------------------------------------------- | -------------- |
| データ分類                     | orders: `confidential`、tenant registry: `confidential`、audit: `restricted` | データ分類基準 |
| PIIの有無と種類                | 注文に担当者氏名・メールアドレス（B2B担当者）                                | 設計           |
| 規制                           | 個人情報保護法。silo 2テナントは金融業界ガイドライン                         | 契約           |
| 現在のデータ量                 | 1,200万item、25GB                                                            | 現行DB         |
| 12ヶ月後のデータ量             | 4,000万item、80GB                                                            | 成長予測       |
| item size                      | 2KB / 32KB                                                                   | 設計           |
| 保持期間 / 削除要件            | 注文7年（法定）、ログ90日、audit 1年以上                                     | 法務           |
| テナント削除時のデータ削除要件 | 契約終了後90日以内                                                           | 契約           |
| 暗号化要件                     | サービスCMK。silo 2テナントはtenant別CMK                                     | 契約           |
| RPO / RTO                      | RPO 5分（PITR）/ RTO 1時間                                                   | 事業要件       |

### 6. SLO

| SLI                                       | 目標                  | window | 除外条件                                         |
| ----------------------------------------- | --------------------- | ------ | ------------------------------------------------ |
| availability（order API）                 | 99.9%                 | 30d    | 計画メンテナンス、クライアント起因4xx（429除く） |
| latency p95（createOrder）                | 300ms                 | 30d    | 同上                                             |
| latency p99（createOrder）                | 800ms                 | 30d    | 同上                                             |
| latency p99（getOrder）                   | 300ms                 | 30d    | 同上                                             |
| 処理開始遅延 p95（premium queue）         | 60s                   | 30d    | —                                                |
| 処理開始遅延 p95（standard queue）        | 300s                  | 30d    | —                                                |
| end-to-end遅延 p95（created → fulfilled） | 5分                   | 30d    | 外部履行API障害（SLO外、別途alarm）              |
| provisioning workflow成功率               | 99%（補償成功を含む） | 30d    | —                                                |

| 項目                | 値                                                                      |
| ------------------- | ----------------------------------------------------------------------- |
| error budget policy | 残量25%未満で新機能リリース凍結、信頼性改善を優先。枯渇で全リリース停止 |
| 契約上のSLA         | premium 99.5% availability（SLOは99.9%でSLAより厳しい）                 |
